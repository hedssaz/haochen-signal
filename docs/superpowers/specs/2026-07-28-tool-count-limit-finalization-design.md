# 工具计数与上限收尾设计

## 目标

在不重新展开工具详情的前提下，让用户随时知道当前任务已经调用了多少次工具；工具调用达到上限时，不再立即以错误结束，而是让 Agent 基于已有结果完成一次最终说明。

## 交互

- 每个任务开始时工具计数归零。
- 每收到一次真实 `tool_started`，计数加一。
- 任务运行期间，黄色状态行显示 `工具 当前次数/上限 次`，例如：

  `状态 › 运行中 · 正在规划 · 工具 12/32 次 · Ctrl+C 中止`

- 工具明细继续沿用现有的单行展示和回答开始后的自动收起。
- 达到工具上限时，状态切换为“工具已达上限，正在整理最终回答”，随后显示 Agent 的正常最终回答，不新增红色“达到上限”终止项。

## 上限收尾

当一批工具调用执行到预算边界时：

1. 已进入 `tool_started` 的调用正常执行并计数。
2. 超出预算的调用不执行，也不计数。
3. 为未执行的调用补齐内部工具结果，明确说明“工具调用上限已达到，本次调用未执行”，保证模型消息协议完整。
4. 向模型追加一条内部系统说明，要求它停止调用工具，基于已有信息总结已完成内容、当前结论和未完成项。
5. 额外允许一次不提供工具定义、`toolChoice: none` 的收尾请求；该请求不受原轮次上限阻断。
6. 如果模型在收尾请求中仍返回工具调用，任务以明确协议错误结束，避免循环。

工具上限只限制真实执行次数，不把被拒绝的溢出调用计入底栏。

## 状态与边界

- `UiState` 保存本任务的工具调用计数，由 `task_started` 重置、`tool_started` 递增。
- CLI 从运行配置读取最大工具调用数并传给界面，避免写死 `32`。
- 轮次上限维持现有直接停止行为；本次只调整工具调用上限。
- 用户中止、模型网络错误和工具执行错误保持现有处理方式。

## 方案取舍

- 不从转录记录反推计数：回答开始后工具记录会被收起，反推结果不可靠。
- 不在达到上限后自动创建新任务：会破坏单任务边界，也可能绕过预算。
- 选择一次无工具收尾轮：既能让 Agent 向用户交代进度，又保证不会继续执行工具。

## 验证

- Reducer 测试：任务开始归零、每个 `tool_started` 只加一次。
- CLI 渲染测试：状态行显示当前次数和最大次数。
- Agent 循环测试：只执行预算内调用，溢出调用不执行；随后发起一次 `toolChoice: none` 的收尾请求并输出最终回答。
- 防循环测试：收尾轮仍请求工具时明确失败。
- 完整测试、类型检查和构建全部通过。
